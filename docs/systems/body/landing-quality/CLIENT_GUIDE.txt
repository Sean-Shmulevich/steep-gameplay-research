Landing amount and display quality

This module calculates the scalar used by the landing-quality display and
applies the selected ordered range table. Run python3 reference.py for examples.
It needs only reference.py and named_data.json.

Amount calculation

Let H be the landing history input, S the material lookup multiplier, C the
landing conversion, and J the optional contribution:

    amount = (S*H)*C
    if optional contribution is not suppressed: amount += J

Each multiplication and addition uses float32 rounding in reference.py. For
the supplied normal configuration, C=0.0026249999646095037. The material lookup
uses default S=1; material identifier 4 uses S=1.2000000476837158. Other selected
configurations may supply different values through the function arguments.
With H=4000, the default material yields 10.5 and material 4 yields approximately
12.6. These H values are supplied illustrative states, not measured play data.

H comes from the landing history calculation rather than instantaneous speed.
The input is a scaled history of negative changes in squared speed. This module
accepts H explicitly and does not invent a new sampling-history algorithm.
A negative H or absent player skips the amount event on this path. The
acceptance return for either shortcut is true; no amount or display category
is generated by that shortcut. Python represents this by amount=None.

The optional contribution is evaluated separately from a selected curve unless
a bound behavior predicate suppresses it. J here is the resulting contribution,
not that curve's input. body/landing-producers now traces that curve input through a saved elapsed-state
record and the evaluation-window snapshot. Its physical time unit remains
unspecified. This local API still accepts J or explicit suppression. No named
physical G unit is inferred from a curve's title alone.

Amount, event and display ordering

The amount is published as a landing-amount event before the crash-load
accumulator processes that same amount. The display listener consumes this
current-event amount, not the accumulated crash load. Its existing category
updates only while both listener and service are enabled and display_mode=1.
In other modes, it retains its prior category.

The selected table is scanned in stored order:

    for item in ranges:
        if item.minimum <= amount < item.maximum:
            return item.category
    return 0

Lower bounds are inclusive and upper bounds exclusive. Overlapping intervals
choose the first stored match. An empty table also returns 0. The supplied table
is used by SnowboardScoring, which the configuration registry selects for both
snowboard and ski activities:

    category 1: [0,3)
    category 2: [3,5)
    category 3: [5,9999)

Therefore amount 3 selects category 2, amount 5 selects category 3, and amount 9999
returns 0. The table's numerical categories are retained here. A clean/sketchy/
crash label mapping is not supplied; these names must not be assigned by guess.
Display_mode is likewise kept numerical instead of inventing a state name.

Display quality and crash acceptance

For the supplied BigAir crash-load settings, an amount adds to the ordinary
landing load only when amount>9. Thus amount 7 and amount 9 both select display
category 3 while neither passes that load-addition threshold. A display category
alone does not determine actual crash failure. Failure also depends on existing
load, grace branches, accumulator limits and the selected failure configuration.
Those complete failure rules are separate from this display range selector.

Examples and input boundaries

reference.py demonstrates exact range boundaries, preservation outside display
mode 1, normal/material 4 amount calculation, and optional-term suppression.
Its illustrative optional contribution 2 is explicitly supplied, not an authored
curve output. Inputs are finite scalar values; vector/contact geometry and
clock integration are outside this small module.

The arithmetic and event gates have 3,000 isolated checks: 2,000 selector cases
include ordered overlaps and exact boundaries, and 1,000 display-event cases
exercise mode/listener/service gates. The selected-service provider is an
external boundary in those checks. They do not simulate complete gameplay.

Unspecified inputs and limits

Category labels, the optional curve-input unit, complete recovery destination
state names, automatic respawn timing/placement and ragdoll handoff remain
unspecified. This module closes landing amount to numerical display quality;
it does not attach new meanings to those unrelated transitions.

# Ground-response helper testbench

This runner executes the reconstructed helper on explicit observations. It does
not launch the game, select a live profile, integrate a ride, apply impulses to
the prototype, or prove full-engine equivalence. Its numerical basis and validation
are in the [central impulse guide](CENTRAL_IMPULSE.md#composed-helper-contract).

## Run a sequence

From the repository root:

```sh
python3 -m engine.ground_response_bench \
  --request engine/examples/ground_response_probe.json \
  --output ground-response-result.json
```

The bundled request contains five synthetic velocity observations and constant
synthetic curves. It demonstrates history/filter evolution while producing ordered
impulse plans. The observations are not generated by those impulses. Replace them
with measured or intentionally supplied inputs to investigate a specific case.
No original tuning data is included in the example.

The same function is available as `engine.ground_response_bench.run(request)`.
With the ordinary inspector running through `python3 -m engine.cli --serve`, POST
JSON to `/` with `{"op":"ground_response","request": ...}`. Inspection does not
change the server's simulation state. Invalid requests return HTTP 400.

## Request contract

- `initial_state`: previous/current velocity XYZ, rate and displacement.
- `frames`: 1 to 2400 explicit updates. Each contains `observation`, `force` and
  `submission`, using the [composed helper fields](../../reference/ground_response.py).
  Each observation has a positive dt no greater than one second. These are
  testbench bounds, not original-engine gates.
- `curve_format`: `sampled` or `compiled`. Sampled input uses the three selected
  ground-stick settings fields with `domain` and `$array`, up to 4097 samples.
  Compiled input uses `entry`, `a` and `b`, each with `start`, positive
  `index_scale`, and up to 4096 `[slope, intercept]` segments.
- `rsqrt_policy`: explicitly choose `supplied` or `sqrt_seed`. The supplied policy
  consumes each frame's `rsqrt_estimates` in native normalization order and rejects
  missing or unused estimates. The sqrt policy uses float32 `1/sqrt(n)` as a
  declared derived seed. It must not be labeled processor-RSQRT equivalent.

Captured estimates remain caller data unless their provenance has been validated.
The testbench does not promote a supplied array to native evidence. Profile data
also remain caller-owned; sport/profile selection is outside this interface.

## Results and repeated testing

Each frame includes next state, entry result, geometry and scalar results when
executed, ordered rider/main impulse plans, publication, and estimates used.
The final state can become the initial state of a subsequent sequence. Input JSON
receives a canonical SHA-256 for comparison; output labels distinguish this
reconstruction from live game execution. No body mutations are performed.

The runner carries helper history and filter state across frames. It does not
feed its impulse plan back into the next supplied velocity sample. That would
require a declared rigid-body/contact integration policy or an observed game
sample. This separation prevents silently inventing the missing world response.

Tests exercise the actual CLI and loopback route, input immutability,
repeatability, sampled/compiled curve input, estimate accounting, limits, failure
responses, and nonmutation of the prototype on both successful and failed
inspection. Original-instruction evidence for the underlying helper remains
separate from these interface tests.
